# Schema Report — Agent 1

Generated by exploring `public.customers` and `public.transactions` via the Supabase MCP
connector, project `gn-dataproject`. Read-only queries only.

Note: `public.dsm` also exists (3,000 rows, same shape as `transactions`) but is a
redundant staging table — not used anywhere in this pipeline.

## The Customer_ID link

There's no database-enforced foreign key between the tables, so I checked it directly:
every one of the 3,000 transactions has a `Customer_ID` that matches a real row in
`customers`. **Zero orphan transactions.** The link is clean even though it isn't enforced.

## How many customers actually bought something

- 954 of the 1,000 customers have at least one transaction (46 customers have never bought anything).
- Average transactions per active customer: **3.14**.
- Most transactions by a single customer: **10**.

## Nulls

**Zero nulls anywhere** — every column in both `customers` and `transactions` is fully
populated (checked column by column). This is unusually clean data; worth keeping in mind
that a real production dataset would likely have some.

## Date range

Earliest purchase: **2021-03-25**. Latest purchase: **2023-03-25**. Exactly a 2-year span,
computed with `to_date("Date_of_Purchase", 'DD-MM-YYYY')` — never sorted as raw text.

## What this means for the next agent

- No cleanup needed for orphans or nulls — the data is already consistent.
- `Age` and `Location` are usable for segmentation in Agent 2 (no nulls to handle).
- 46 customers with zero transactions exist in `customers` but won't appear in any
  revenue breakdown — that's expected, not a bug.
